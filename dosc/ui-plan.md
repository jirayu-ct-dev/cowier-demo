# แผนพัฒนา UI ระบบ CWIE BRU

เอกสารนี้เป็นลำดับการพัฒนา UI ทั้งระบบด้วย Mock Data โดยจบและตรวจรับทีละ
Checkpoint ก่อนเริ่มขั้นถัดไป ระยะนี้ยังไม่เชื่อม Backend, Database หรือ File Storage จริง

## 1. เป้าหมายของแผน

- ตรวจ Flow และ Requirement ผ่านหน้าจอที่กดใช้งานได้จริง
- พบสิ่งที่ต้องปรับก่อนออกแบบ API และ Database schema
- ทำงานเป็น Vertical Slice ตามกระบวนการธุรกิจ ไม่สร้างทุกหน้าแบบครึ่งสำเร็จพร้อมกัน
- ให้เจ้าของระบบตรวจคำศัพท์ ข้อมูลที่แสดง ลำดับงาน สิทธิ์ และสถานะทุกช่วง
- เมื่อจบระยะ UI ต้องเปลี่ยน Mock Data เป็น API ได้โดยไม่รื้อ Page และ Component

## 2. กติกาการทำงานแต่ละ Checkpoint

ใช้วงรอบเดียวกันทุกขั้น:

```text
ยืนยันขอบเขตขั้นนั้น
  → พัฒนา UI และ Mock interaction
    → ตรวจ build และสถานะสำคัญ
      → ส่ง URL + Scenario + รายการที่ต้องตรวจให้เจ้าของระบบ
        → แก้ตาม Feedback
          → เจ้าของระบบยืนยัน
            → ล็อก Requirement ของขั้นนั้นและเริ่มขั้นถัดไป
```

ระหว่างรอการตรวจจะไม่เริ่ม Feature ถัดไปที่พึ่งพา Flow เดิม เพื่อไม่ให้การแก้ Requirement
ลามไปหลายส่วนพร้อมกัน หากเป็นการแก้ Design System ที่ไม่เปลี่ยน Flow สามารถแก้ร่วมกันได้

ทุกครั้งที่ส่งตรวจต้องระบุ:

- URL ของหน้าที่ต้องเปิด
- บทบาทและ Mock scenario ที่ต้องเลือก
- สิ่งที่ทำงานได้และสิ่งที่ยังเป็น Mock
- Happy path และกรณีผิดพลาดที่ควรลอง
- รายการคำถามที่ต้องการคำยืนยัน
- Screenshot ของ Desktop และ Mobile สำหรับหน้าหลัก
- ผล `pnpm build` และข้อจำกัดที่ยังเหลือ

## 3. Definition of Done ของทุก Checkpoint

Checkpoint จะถือว่าเสร็จเมื่อ:

- หน้าที่อยู่ในขอบเขตมี Loading, Empty, Error และ Data state ครบ
- Form มี label, help text, inline validation และป้องกันการ submit ซ้ำ
- Action สำคัญมี confirmation หรือ feedback ที่เหมาะสม
- รองรับอย่างน้อย Mobile และ Desktop โดยไม่เกิด horizontal overflow ที่ไม่ตั้งใจ
- ใช้ keyboard ได้ มี focus-visible และ Dialog คืน focus ถูกตำแหน่ง
- ข้อความ สถานะ และสิทธิ์ตรงกับ `dosc/requirement.md`
- Mock mutation สะท้อน state transition จริงและมีปุ่ม Reset scenario
- ไม่มีลิงก์หรือปุ่มที่ดูเหมือนใช้งานได้แต่ไม่มีผล
- `pnpm build` ผ่าน และไม่มี error ใน browser console ของ Flow ที่ส่งตรวจ
- เจ้าของระบบตรวจและตอบยืนยันให้เริ่ม Checkpoint ถัดไป

## 4. Mock Environment สำหรับตรวจ UI

สร้าง Developer Scenario Panel ที่แสดงเฉพาะ development mode เพื่อให้ตรวจได้โดยไม่ต้อง
แก้ไฟล์ข้อมูลทุกครั้ง ประกอบด้วย:

- เลือกบทบาท Staff, Lecturer หรือ Student
- เลือกผู้ใช้ตัวอย่างและรอบสหกิจปัจจุบัน
- เลือกชุดข้อมูล Normal, Empty, Long content หรือ Edge case
- จำลอง network delay และ force error
- Reset ข้อมูลกลับสู่ค่าเริ่มต้น
- เปิดดูรายการ notification/event ที่ Mock action สร้างขึ้น

Mock data อยู่ใน memory และ reset เมื่อ reload ได้ ไม่ใช้ local storage เป็นฐานข้อมูลจำลอง
กลไกเลือกบทบาทนี้ใช้เพื่อตรวจ UI เท่านั้นและต้องไม่ถูกนำไปใช้เป็นระบบสิทธิ์จริง

## 6. ลำดับการพัฒนาและจุดตรวจรับ

### Checkpoint 0 — ยืนยัน Information Architecture

**ผลลัพธ์**

- แผนฉบับนี้ Route map ลำดับงาน และคำศัพท์เมนู
- UI ภาษาไทย และใช้ชื่อระบบ **CWIE BRU** แบบตัวอักษรในช่วงที่ยังไม่มีตราสัญลักษณ์
- Brand color foundation:
  - Primary accent: `#F5B32B`
  - Main background: `#FFFFFF`
  - Secondary background: `#F7F7F7`
  - Sidebar background และข้อความบน primary: `#1D1E20`
  - Border / divider: `#E5E7E9`
- ปุ่ม primary ใช้ข้อความสีเข้ม `#1D1E20` บนพื้น `#F5B32B`; ไม่ใช้ข้อความสีขาวบนสี
  primary เพราะคอนทราสต์ไม่เพียงพอ
- สี success, warning, error และ info เป็น semantic colors แยกจาก primary accent และต้องไม่สื่อ
  ความหมายด้วยสีเพียงอย่างเดียว
- แผน Responsive: นักศึกษา mobile-first; เจ้าหน้าที่เน้น desktop แต่ใช้ mobile ได้;
  อาจารย์รองรับทั้งสองขนาด

**เจ้าของระบบตรวจ**

- ชื่อเมนูเข้าใจง่ายและตรงกับงานจริงหรือไม่
- มีหน้าที่ไม่ควรมีหรือหน้าที่ตกหล่นหรือไม่
- ยอมรับลำดับ Checkpoint และค่าเริ่มต้นด้านภาพหรือไม่

**ผ่านเมื่อ** Route map และลำดับงานได้รับการยืนยัน รอบนี้ยังไม่มี UI code

### Checkpoint 1 — Design Foundation และ App Shell

**สถานะ:** ผ่านการตรวจรับแล้ว — ใช้เป็น UI contract กลางของทุกหน้าถัดไป

**พัฒนา**

- Semantic tokens: สีพื้นผิว ตัวอักษร เส้นขอบ primary และสถานะ
- สร้าง token จากชุดสี CWIE BRU แทนการใส่ค่าสี hex กระจายในแต่ละ component
- Typography, spacing, radius, shadow และ responsive breakpoints
- UI primitives ที่จำเป็นรอบแรก: Button, Input, Textarea, Select, Checkbox,
  Radio, Badge, Card, Alert, Dialog, Drawer, Dropdown, Tabs, Toast, Skeleton
- Pattern ตารางข้อมูล: search, filter, sort, pagination, bulk selection และ mobile card
- Shared states: Loading, Empty, No results, Error, Forbidden
- App shell, sidebar, top bar, mobile navigation, breadcrumb และ user menu
- Developer Scenario Panel
- Component showcase route เฉพาะ development

**เจ้าของระบบตรวจ**

- สี ขนาดตัวอักษร ความหนาแน่น และความเป็นทางการ
- Sidebar/Desktop และ Mobile navigation
- รูปแบบ Button, Form, Table/Card, Dialog และข้อความแจ้งผล
- การอ่านภาษาไทยและความชัดเจนของสถานะ

**ผ่านเมื่อ** รูปแบบกลางได้รับอนุมัติและใช้เป็นฐานของทุกหน้าถัดไป

**ผลการตรวจรับ:** เจ้าของระบบยืนยันให้ยึดรูปแบบ UI ของ Checkpoint 1
เป็นมาตรฐานสำหรับทุกหน้า การพัฒนาขั้นถัดไปต้องใช้ semantic tokens, app shell,
องค์ประกอบฟอร์ม ตาราง สถานะ การตอบสนองบน Mobile/Desktop และ interaction pattern
จาก Design System นี้ก่อนสร้างรูปแบบใหม่ หากจำเป็นต้องเปลี่ยน pattern กลาง
ต้องแจ้งผลกระทบและนำกลับมาตรวจในหน้า `/dev/ui` ก่อนนำไปใช้ทั้งระบบ

### Checkpoint 2 — Flow ยื่นสถานประกอบการ: ฝั่งนักศึกษา

**สถานะ:** พัฒนา UI และ Mock interaction แล้ว — รอเจ้าของระบบตรวจรับ

**พัฒนา**

- หน้ารายการและประวัติคำร้องของตนเอง
- ค้นหาและเลือกสถานประกอบการ
- Empty search → เพิ่มสถานประกอบการใหม่ ชื่อ ที่อยู่ จังหวัด
- Form คำร้อง: ตำแหน่ง รายละเอียด (ไม่บังคับ) วันที่สมัคร ผู้รับ ตำแหน่ง/หน่วยงาน และที่อยู่หนังสือ
- บันทึกฉบับร่าง ส่งคำร้อง แก้ไข และยกเลิกตามสถานะที่อนุญาต
- หน้ารายละเอียดแสดง timeline, สถานะคำร้อง และเหตุผลที่ส่งกลับ

**Scenario สำคัญ**

- พบ/ไม่พบสถานประกอบการ
- สถานประกอบการรอตรวจสอบหรือยุติการใช้งาน
- มีคำร้องเดิมที่ยังดำเนินการอยู่ และป้องกันการสร้างคำร้องใหม่จนกว่าจะสิ้นสุดหรือยกเลิก
- คำร้องแก้ไขได้ ถูกล็อก หรือออกหนังสือแล้ว
- Form validation และ mock submit error

**เจ้าของระบบตรวจ**

- ข้อมูลที่นักศึกษาต้องกรอกและลำดับของ Form
- คำศัพท์ของทุกสถานะและข้อความอธิบายสิ่งที่ต้องทำต่อ
- ข้อมูลผู้รับหนังสือแยกจากข้อมูลหลักของสถานประกอบการชัดเจนหรือไม่

**ผ่านเมื่อ** นักศึกษาสร้างและติดตามคำร้องได้ครบจนถึงสถานะรอเจ้าหน้าที่

### Checkpoint 3 — Flow ชุดหนังสือ: ฝั่งเจ้าหน้าที่และนักศึกษา

แบ่งส่งตรวจ 3 ครั้งย่อยเพื่อลดขนาดการแก้ไข:

#### 3A เจ้าหน้าที่ตรวจคำร้องและสถานประกอบการ

- Queue คำร้องพร้อม search/filter/sort
- ตรวจ แก้ไข ยืนยัน และรวมสถานประกอบการซ้ำ
- ดูความเข้ากันได้ของคำร้องก่อนรวมชุดหนังสือ
- ส่งกลับแก้ไขพร้อมเหตุผล

#### 3B เจ้าหน้าที่สร้างและเผยแพร่ชุดหนังสือ

- เลือกคำร้องที่อยู่รอบ บริษัท สาขา ผู้รับ และที่อยู่เดียวกัน
- แสดงรายชื่อนักศึกษาและตำแหน่งในชุด
- เลือกผู้ประสานงานของชุดได้แบบไม่บังคับ
- ใส่เลขที่/วันที่หนังสือ แนบ Mock PDF และเผยแพร่
- ล็อกรายชื่อ ยกเลิกฉบับเดิม และแสดงประวัติรุ่นเอกสาร
- แสดงสถานะของชุดหนังสือและสถานะผลรายบุคคลแยกจากกัน

#### 3C นักศึกษาตอบกลับและเจ้าหน้าที่ยืนยันรายบุคคล

- นักศึกษาทุกคนในชุดเห็น PDF และข้อมูลร่วมกัน
- นักศึกษาคนใดคนหนึ่งอัปโหลด Mock signed PDF หรือฉบับแทนที่
- เจ้าหน้าที่ส่งกลับแก้ไข ยืนยัน หรือไม่ได้รับตอบรับเป็นรายบุคคล
- ปิดคำร้องอื่นเมื่อมีสถานประกอบการที่ยืนยันแล้ว

**เจ้าของระบบตรวจ**

- วิธีเลือกและรวมคำร้องไม่ทำให้เข้าใจผิดว่าเป็นการสมัครแทนกัน
- ความต่างระหว่างสถานะชุดหนังสือ เอกสาร และผลรายบุคคล
- ผู้ที่มีสิทธิ์เห็น/อัปโหลดไฟล์และประวัติไฟล์

**ผ่านเมื่อ** Flow ตั้งแต่นักศึกษาส่งคำร้องจนยืนยันสถานที่ฝึกงานทำได้ end-to-end

---

### Checkpoint 4 — รอบสหกิจและสถานะการปฏิบัติงาน

**พัฒนา**

- รายการ/รายละเอียดรอบ ปีการศึกษา ภาคเรียน รุ่น และช่วงวันที่
- สถานะ Draft → Open → Closed to new requests → Training → Closed
- เพิ่มนักศึกษาเข้ารอบรายคน/หลายคน
- ย้ายรอบพร้อมเหตุผลและแสดงประวัติ
- ปรับสถานะการปฏิบัติงานรายบุคคลพร้อมเหตุผล
- Student ดูสถานะการปฏิบัติงานและสถานประกอบการที่ยืนยันของตนเอง
- ป้องกันการอยู่ในรอบที่กำลังดำเนินการมากกว่าหนึ่งรอบใน Mock flow

**เจ้าของระบบตรวจ**

- คำศัพท์และ action ที่อนุญาตในแต่ละสถานะรอบ
- วิธีเลือกหลายคนและวิธีย้ายรอบ
- การมองเห็นประวัติและสถานะการฝึกของนักศึกษา

**ผ่านเมื่อ** เจ้าหน้าที่ควบคุมบริบทของรอบที่ Placement และ Supervision ใช้ได้ครบ

### Checkpoint 5 — Master Data, Account และ Import/Export

แบ่งส่งตรวจ 2 ครั้งย่อย:

#### 5A ข้อมูลหลักและบัญชี

- นักศึกษา อาจารย์ สถานประกอบการ: table/card, search, filter, detail, add, edit
- ยุติ/เปิดใช้งานโดยไม่ลบจริง พร้อมผลกระทบที่อธิบายชัดเจน
- Lecturer search/filter/view student and placement history และแก้ไขได้เฉพาะชื่อ/นามสกุล
- สถานะบัญชี ระงับ ยุติการใช้งาน และ Mock reset password
- ประวัติกิจกรรมบัญชีและการเปลี่ยนข้อมูล แสดงผู้ดำเนินการ เวลา ค่าเดิม และค่าใหม่

#### 5B Import/Export

- เลือก CSV/XLSX และ preview รายการถูกต้อง ซ้ำ และไม่ถูกต้อง
- Filter ตามผลตรวจและแสดงเหตุผลรายแถว
- Confirm เฉพาะรายการที่ถูกต้องและหน้าสรุปหลังนำเข้า
- Mock download template, error rows และ export data

**เจ้าของระบบตรวจ**

- คอลัมน์ขั้นต่ำและรายละเอียดในหน้าข้อมูล
- ขอบเขตการแก้ไขของ Staff กับ Lecturer
- คำเตือนก่อนยุติการใช้งานและผลกระทบต่อประวัติ
- ความเข้าใจง่ายของ Import preview และรายการผิดพลาด

**ผ่านเมื่อ** งานจัดการข้อมูลต้นทางที่ใช้ในทุก Flow ครบตามขอบเขต

### Checkpoint 6 — เจ้าหน้าที่จัดกลุ่มและตารางนิเทศ

แบ่งส่งตรวจ 3 ครั้งย่อย:

#### 6A จัดกลุ่มนิเทศ

- เลือกรอบ ครั้งที่ 1/2 และกรองตามภูมิภาค จังหวัด บริษัท
- กำหนดพื้นที่รับผิดชอบอาจารย์ตามภูมิภาค จังหวัด หรือสถานประกอบการ
- สร้างกลุ่มและกำหนดอาจารย์รับผิดชอบหลัก
- แสดงนักศึกษาที่ได้รับยืนยันแล้วและยังไม่ถูกจัดรายการ
- กลุ่มครั้งที่ 1/2 แยกกันโดยไม่ copy อัตโนมัติ

#### 6B สร้างรายการนัดและตรวจ Conflict

- ระบุบริษัท นักศึกษา วันที่ ช่วงเช้า/บ่าย และผู้เข้าร่วม
- เพิ่มอาจารย์จากกลุ่มอื่นเฉพาะรายการ
- แสดง conflict ของกลุ่ม อาจารย์ นักศึกษา และบริษัทก่อนบันทึก
- แยกนักศึกษาบริษัท/สาขาเดียวกันได้เมื่อระบุเหตุผล

#### 6C เผยแพร่และจัดการการเปลี่ยนแปลง

- Draft preview และ publish confirmation
- เปลี่ยนวัน/ช่วงเวลา/ผู้เข้าร่วมพร้อมดูค่าเดิม-ใหม่
- เลื่อนแบบไม่มีวันใหม่ ยกเลิก และแจ้งผู้ได้รับผลกระทบ
- Calendar/list view แยกครั้งที่ 1 และ 2

**เจ้าของระบบตรวจ**

- วิธีจัดกลุ่มและคัดกรองตรงกับวิธีทำงานจริงหรือไม่
- มองเห็นตารางชนและสาเหตุได้เร็วพอหรือไม่
- ขั้นตอนแก้ตารางหลังเผยแพร่และผลกระทบชัดเจนหรือไม่

**ผ่านเมื่อ** Staff วางและเผยแพร่ตารางได้ครบโดยไม่เกิด conflict ใน Mock flow

### Checkpoint 7 — การใช้งานตารางและบันทึกผลนิเทศ

**พัฒนา**

- Lecturer: ตารางของตน รายละเอียดรายการ และข้อมูลนักศึกษา/บริษัทที่เกี่ยวข้อง
- Lecturer/Staff: แก้ผู้เข้าร่วม วันที่ และช่วงเวลาตามสิทธิ์
- บันทึกผล ปัญหา ข้อเสนอแนะ และ Requirement ของบริษัท
- ยืนยันอาจารย์ที่เข้าร่วมจริงก่อนเปลี่ยนเป็น Completed
- ล็อกวัน เวลา นักศึกษา และผู้เข้าร่วมจริงหลัง Completed
- Student: ดูเฉพาะนัดของตนและเพื่อนในบริษัท/รายการเดียวกัน
- Student ไม่เห็นงบประมาณ บันทึก หรือคะแนนประเมิน

**เจ้าของระบบตรวจ**

- ข้อมูลที่อาจารย์ต้องเห็นก่อนและหลังไปนิเทศ
- ลำดับการยืนยันผู้เข้าร่วมจริงและการล็อกข้อมูล
- ข้อมูลของเพื่อนที่นักศึกษามองเห็นได้เหมาะสมหรือไม่

**ผ่านเมื่อ** Appointment เดินจาก Waiting/Postponed ไป Completed ได้ครบตามสิทธิ์

---

### Checkpoint 8 — งบประมาณประมาณการ

**พัฒนา**

- Staff-only budget ต่อกลุ่มนิเทศ
- รายการเบี้ยเลี้ยง ที่พัก เดินทาง และค่าใช้จ่ายอื่นแบบเพิ่มแถวได้
- ชื่อรายการ จำนวนเงิน หมายเหตุ ลบ/แก้แถว และผลรวมรายหมวด/รวมทั้งหมด
- Validation จำนวนเงินไม่ติดลบและไม่นับช่องว่าง
- Empty state และ summary ที่อ่านได้บน Desktop/Mobile

**เจ้าของระบบตรวจ**

- วิธีเพิ่มค่าใช้จ่ายอื่นและการจัดกลุ่มยอดรวม
- ข้อมูลเพียงพอสำหรับ “งบประมาณประมาณการ” โดยไม่กลายเป็นระบบเบิกจ่ายหรือไม่

**ผ่านเมื่อ** เจ้าหน้าที่จัดงบประมาณกลุ่มได้ครบและ Role อื่นเข้าถึงไม่ได้ใน UI

---

### Checkpoint 9 — แบบประเมินและการติดตามความครบถ้วน

แบ่งส่งตรวจ 2 ครั้งย่อย:

#### 9A อาจารย์ทำแบบประเมิน

- Task list แสดงนักศึกษาและบริษัทที่ตนยังต้องประเมิน
- แบบประเมินนักศึกษารายบุคคล 7 หัวข้อ ระดับ 1–5/ประเมินไม่ได้
- แบบประเมินบริษัท 7 หัวข้อและข้อความเพิ่มเติม
- Save draft, validation ก่อน submit, summary และ confirmation
- ส่งแล้วเป็น read-only และไม่แสดงแบบของอาจารย์คนอื่น

#### 9B เจ้าหน้าที่ติดตามผล

- สถานะ Not started/In progress/Complete ต่อรายการนัด
- Matrix ผู้เข้าร่วมจริง × นักศึกษา × แบบประเมินบริษัท
- ดูผลและค่าเฉลี่ยโดยไม่นับหัวข้อที่ประเมินไม่ได้
- Student ไม่มีหน้าคะแนนหรือผลประเมิน

**เจ้าของระบบตรวจ**

- คำอธิบายระดับคะแนนและลำดับหัวข้อ
- ข้อความเสริมที่จำเป็นในแบบนักศึกษา/บริษัท
- การแสดงงานค้างและค่าเฉลี่ยเข้าใจง่ายหรือไม่

**ผ่านเมื่อ** อาจารย์ทุกคนใน Mock scenario ส่งงานครบและสถานะรายการเปลี่ยนถูกต้อง

### Checkpoint 10 — Notification, Dashboard และ Authentication UI

แบ่งส่งตรวจ 2 ครั้งย่อย:

#### 10A Notification และ Dashboard

- Notification center, unread count, mark as read และ deep link
- Event จาก Placement/Supervision ที่ทำไว้ก่อนหน้าปรากฏในรายการ
- Dashboard ของแต่ละบทบาทแสดงงานที่ต้องทำ สถานะสำคัญ และนัดถัดไป
- Dashboard ไม่สร้างรายงานใหม่ที่อยู่นอก Requirement

#### 10B Login และ Account flow

- Login, generic error, temporary lock message และ account state messages
- First login/temporary password → forced password change
- Change password และ Staff reset password dialog
- Mock redirect ตามบทบาทและ forbidden page

**เจ้าของระบบตรวจ**

- ความสำคัญและลำดับข้อมูลบน Dashboard
- Notification ใดควรอ่านแล้ว/ยังไม่อ่านและ deep link ไปหน้าถูกต้องหรือไม่
- ข้อความ Login/Password เข้าใจง่ายโดยไม่เปิดเผยข้อมูลบัญชีเกินจำเป็น

**ผ่านเมื่อ** ผู้ใช้เริ่มจาก Login และเข้าถึงทุก Flow ตามบทบาทผ่าน navigation ได้

### Checkpoint 11 — Final UI Acceptance

**พัฒนาและตรวจรวม**

- Walkthrough end-to-end ของ 3 บทบาทและ 2 ครั้งการนิเทศ
- ตรวจทุก state, permission boundary และ deep link
- Responsive pass ที่ 360px, tablet และ desktop
- Keyboard/focus, contrast, reduced motion และข้อความภาษาไทยยาว
- Loading/error delay, duplicate submit และ reset scenario
- ลบ component/style ซ้ำ และยืนยันว่าไม่มี dead route/action
- ตรวจว่าไม่มีหน้ารายงาน การเบิกจ่าย หรือ flow เปลี่ยนบริษัทกลางฝึกที่อยู่นอก scope
- สรุป Screen inventory และ Requirement-to-screen matrix ฉบับสุดท้าย

**เจ้าของระบบตรวจ**

- ทดสอบ Acceptance scenario ที่เตรียมไว้โดยไม่ต้องอ่านโค้ด
- แจ้งเฉพาะ defect หรือ Requirement gap; การเพิ่ม scope ใหม่แยกเป็นรอบถัดไป

**ผ่านเมื่อ** เจ้าของระบบยืนยัน UI ทั้งระบบ และ Requirement/UI contract พร้อมใช้วาง API
กับ Database schema ในระยะถัดไป

## 7. สิ่งที่ตั้งใจไม่ทำในระยะ UI

- ไม่สร้าง API, Prisma query, migration หรือ MySQL table
- ไม่ทำ Authentication/RBAC ที่ปลอดภัยจริง; มีเพียง UI และ Mock behavior
- ไม่จัดเก็บไฟล์ PDF จริงหรือสร้างหนังสือ PDF ในระบบ
- ไม่ส่ง Notification จริงและไม่ส่ง Email/SMS
- ไม่ทำ Import/Export ที่เขียนข้อมูลลงระบบจริง
- ไม่ทำระบบรายงาน ผลเบิกจ่าย ใบเสร็จ หรืออนุมัติงบประมาณ
- ไม่ทำ Flow เปลี่ยนสถานประกอบการระหว่างฝึกงาน

## 8. การควบคุมการเปลี่ยน Requirement

- Feedback ระหว่าง Checkpoint ให้แก้เอกสาร Requirement ก่อนหรือพร้อมกับ UI
- การเปลี่ยนที่กระทบเฉพาะ Checkpoint ปัจจุบันแก้ให้จบก่อนตรวจซ้ำ
- การเปลี่ยนที่กระทบ Flow ที่ยืนยันแล้ว ต้องแจ้งหน้าที่ได้รับผลกระทบก่อนแก้
- เก็บรายการตัดสินใจสำคัญในเอกสาร ไม่อาศัยเฉพาะข้อความสนทนา
- เมื่อ Checkpoint ผ่าน ให้ใช้คำศัพท์ สถานะ และ interaction เดิมเป็น contract
  ของขั้นถัดไปจนกว่าจะมีการอนุมัติให้เปลี่ยน
